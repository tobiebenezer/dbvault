# DBVault Alpha 0.1 Runbook

**Status:** alpha operating guide  
**Audience:** maintainers, pilot users, early contributors  
**Promise being tested:** install DBVault, open the embedded UI, connect a database/storage pair, run a backup, run a restore drill, and see a protection status.

> DBVault Alpha 0.1 is not production backup software yet. Use it for demos, development environments, staging data, and controlled pilots until the production checklist is complete.

---

## 1. Supported alpha paths

### Native demo path

```bash
make web-build
CGO_ENABLED=0 go build -tags=restricted -o bin/dbvault ./cmd/dbvault
bin/dbvault server --demo --listen 127.0.0.1:8080 --data-dir /tmp/dbvault-demo
```

Open:

```text
http://127.0.0.1:8080
```

### Native install-layout path

This writes into a fake root so it does not touch the host.

```bash
bin/dbvault install \
  --root /tmp/dbvault-install \
  --domain backup.example.test \
  --self-signed
```

Inspect:

```text
/tmp/dbvault-install/etc/dbvault/dbvault.yaml
/tmp/dbvault-install/etc/systemd/system/dbvault.service
/tmp/dbvault-install/var/lib/dbvault/setup-token
```

### Docker demo path

```bash
docker compose -f deploy/compose/demo.yml up --build
```

Open:

```text
http://127.0.0.1:8080
```

## 3. Demo story

Use this script when showing DBVault to someone:

1. Start demo mode.
2. Open the overview page.
3. Show the protection summary.
4. Open the recovery timeline.
5. Run doctor.
6. Trigger policy simulation.
7. Open the repository graph.
8. Show alerts.
9. Create a support bundle.
10. Create a recovery bundle.

The story is:

> Backups are promises. DBVault tests the promise and shows whether the promise is currently trustworthy.

---

## 4. What is real in Alpha 0.1

The alpha validates the product shell and core appliance direction:

- one Go binary can serve the UI and API
- the UI is source-backed from `web/src`
- installation layout is generated by Go
- setup token exists
- demo mode works
- product-experience APIs are reachable
- Docker demo image exists
- release packaging script exists
- restricted build/test path passes without external modules

---

## 5. What is not yet production real

These are still alpha gaps:

- protection status must be wired to real catalogue evidence
- recovery timeline must be wired to real backup/PITR data
- sandbox restore must run real Docker/Kubernetes restore adapters
- support bundle needs more provider diagnostics
- recovery bundle needs a complete catalogue/repository rebuild workflow
- browser tests must move from route checks to Playwright
- production builds require internet access for Go module downloads and `go.sum`
- real R2 and Contabo contract tests must run in an external environment
- PostgreSQL and MySQL logical/physical restore tests must run against real databases

---

## 6. Pilot-user rule

For early pilots, require the user to have an existing backup path outside DBVault.

Do not position DBVault Alpha as the sole backup for irreplaceable production data.

## 8. Success criterion for the next hardening pass

The next pass is successful when one real end-to-end loop works without demo data:

```text
PostgreSQL source
    ↓
Cloudflare R2 or MinIO destination
    ↓
backup
    ↓
restore to sandbox
    ↓
verification
    ↓
Protected status from real evidence
```
